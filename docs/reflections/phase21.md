## 0. 이 Phase 의 성격이 이전과 다르다

Phase 20 의 감사는 **결함**을 찾았다 — 튜너 래칫, 죽은 플래그, 덮어쓰는 아티팩트. 전부
"코드가 의도와 다르게 동작한다"는 형태였다.

2차 감사가 찾은 다섯 중 **셋은 그런 형태가 아니다.**

| | 형태 |
|---|---|
| D63 (비용 규약) · D64 (게이트 운영성) | 고전적 결함 — 배포 경로가 실입력에서 죽거나 쓸 수 없다 |
| **D65 · D66 · D67** | **저장소가 자기 측정으로 이미 가리켜 놓고 따라가지 않은 방향** |

D65: Phase 20 이 예측기 여지를 0% → **9.2%** 로 부호까지 뒤집어 철회했는데, 그 철회에
뒤따르는 코드 경로를 만들지 않았다 (인코더는 CLI 에 하드코딩, `st` 백엔드는 모델명 인자조차
없음).
D66: 제출 기본값이 자기 후보 목록 안의 정책에 지배당하는데 그것을 "문턱 규칙"으로 방어했다.
D67: "fast 퇴화를 완화해도 점수가 안 오른다"까지 측정해 놓고 **"그러므로 다른 tier 로
옮긴다"** 는 다음 문장을 쓰지 않았다.

**교훈 (D68)**: 이 저장소의 자기비판은 *주장*("이 숫자가 진짜인가?")과 *도달 가능성*
("이 코드가 실행되는가?", Phase 20 의 교훈)까지는 심문한다. 그런데 **"이 결론이 우리 다음
행동을 바꿨는가?"** 는 묻지 않는다. 측정 → 결론 → **행동**의 마지막 화살표에 검사 기구가
없다. reflection 이 19편인데 "지난 Phase 의 결론 중 코드에 반영되지 않은 것" 목록이 한 번도
없었던 것이 그 증거다.

## 1. D63 — 배포 차단 결함이 하나 더 남아 있었다

Phase 20 §0 은 원인을 이렇게 진단했다: **"품질 기구가 오프라인 리플레이 경로만 덮는다."**
그리고 `test_deploy_fixes.py` 14종으로 **측정 경계를 넓혔다**고 선언했다.

그 넓힌 경계 밖에 하나가 더 있었다. 대회 상세의 런타임 제공 항목은

    호출 **전**: 프롬프트 · 모델 프로파일 + 공식 **비용 정책**(단가) · 남은 예산·**호출 수**
    호출 **후**: 반환 출력 · 실제 토큰 수 · **실제 비용**

인데 `_cost_vector` 는 후보별 **숫자 비용**만 받았다. 감사가 단가 메타데이터를 주자
`KeyError: 'cost'` 로 첫 스텝에서 죽었다.

★ **가장 아픈 부분**: 저장소는 이 정보 구조를 **이미 알고 있었다.** `src/cost_model.py` 가
"호출 전엔 decode 길이를 모른다"는 제목으로 존재하고, `SUBMISSION §2` 는 "실배포 권장 구성은
`cost_mode='ridge', cost_margin=0.05`" 라고 적는다. **그런데 그 추정기가 배포 경로에 한 줄도
연결돼 있지 않았다.** D36(`text_encoder` 미대입)·D43(생존 모드 미발동)과 **정확히 같은
패턴의 3회차**다 — 문서는 인정했는데 코드 경로가 없다.

왜 안 걸렸나: 오프라인 리플레이는 `cost_mirror.cost_matrix` 로 비용을 **직접 만들어** 쓴다.
어떤 프로브도 "단가에서 비용을 조립"하는 경로를 밟을 이유가 없다.

조치: `CostSpec`(키 이름·단가 단위를 흡수하는 교체 지점 1곳) + 추정기 자동 상속 +
`step(..., remaining_calls=N)`. 그리고 λ 가 오라클 비용으로 튜닝됐는데 배포가 추정 비용을
쓰면 `RuntimeWarning` 을 낸다 — 조용히 다른 정책이 되는 것을 막는다.

## 2. D64 — 점수는 수천 번 쟀는데 **벽시계 시간**은 한 번도 안 쟀다

감사가 `python -m src.gate` 를 1,800쿼리 데이터에 돌렸더니 **900초 동안 표준출력 한 줄 없이**
돌다가 timeout 에 죽었고 **부분 산출물도 0** 이었다.

Phase 20 §4 의 메타 교훈은 "측정은 맞는데 그 측정을 담는 **그릇**이 틀렸다"였다 (아티팩트
덮어쓰기·파일명 충돌·기준 팔 동일). D64 는 같은 문장의 다른 축이다 — **그 측정을 얻는 데
걸리는 시간**은 그릇의 일부인데 아무도 안 봤다. 출품 마감(8/27) 대비 데이터 수령 시점을
생각하면 이것은 편의가 아니라 리스크다.

조치: `--quick`(3-fold×1반복) · stderr 진행 표시 + ETA · **tier 경계마다 부분 판정 저장**.
실측: 같은 데이터·같은 명령이 **253초에 판정 완료**(이전 900초 무결과), 그리고 검증기
AUC 0.65 를 보고 **3 tier 모두 학습형 단일호출을 골랐다** — D60 이 "미지 도메인에서는 순차
기구가 순가치를 못 낸다"고 말한 그 상황에서 게이트가 정확히 설계대로 동작했다.

## 3. D66 — ★ 감사의 진단을 측정이 **반박했다** (그리고 그것이 더 유용했다)

감사 진단: "제출 기본값(selective3 0.5057)이 자기 후보인 cascade-routing(0.5091)에 지배당하는
원인은 **절대 문턱 0.01**이다."

그럴듯했다. 저장소 자신이 §4.5.1 에서 게이트의 절대 문턱 비용을 "+0.005 수준"이라 적어
두었으니 같은 원인으로 보였다. 그래서 `margin_mode="paired_se"`(절대 바닥 제거)를 구현하고
쟀다.

**결과: 효과가 정확히 0.0000 이었다.** 전 정책·전 tier 에서 소수점까지 동일했다.

D55 의 규칙("여러 팔이 동시에 +0.0000 이면 효과 없음이 아니라 **팔이 같다**")대로 발동을
확인했다. 팔은 달랐다 — 구속 조건이 달랐을 뿐이다:

```
fast      격차 +0.0139  쌍대SE 0.0085  요구 0.0100  ← 절대 문턱이 구속
balanced  격차 −0.0347  쌍대SE 0.0183  요구 0.0183  ← SE 가 구속
premium   격차 +0.0243  쌍대SE 0.0134  요구 0.0134  ← SE 가 구속
```

**세 tier 중 둘에서 구속하는 것은 절대 문턱이 아니라 쌍대 SE 였다.** 게이트는 표본을
3,500 으로 키워 SE 가 작아진 체제라 절대 문턱이 구속했고(§4.5.1), `SelectiveRouter` 는
n_sel=288 이라 SE 가 크다. **같은 문장이 두 기구에서 반대로 성립한다.**

### 3.1 그리고 감사 제안을 그대로 넣었더니 점수가 내려갔다

감사는 부수적으로 "`SelectiveRouter` 는 표준오차를 아예 보지 않는다 — 게이트가 D26 에서
배운 것을 여기서는 안 쓴다"고 지적했다. 맞는 지적이라 SE 항을 넣었다(`se_k` 0 → 1).

**결과: selective3 0.5057 → 0.5007 (−0.0050).** 전환 4건 중 2건이 막혔고 **그 둘은 옳은
전환이었다.**

즉 이 체제의 문제는 문턱이 **높아서**가 아니고, 문턱을 더 높이면 손해다.

### 3.2 반대 극단도 재 봤다 — `argmax` 역시 이득이 없다

감사 논리의 극단("대회 목적함수는 기대 점수 최대화이므로 held-out argmax 가 맞다")을
`margin_mode="argmax"`(문턱 0)로 구현해 쟀다.

| 인코더 | `absolute` (0.01) | `argmax` (0) | Δ |
|---|---|---|---|
| hashing96 | **0.5057** | 0.5048 | **−0.0009** |
| hashing512 | 0.5111 | 0.5111 | 0.0000 |

전환이 4 → 5건으로 늘었고 **늘어난 그 한 건이 balanced 를 0.5823 → 0.5795 로 깎았다.**
절대 문턱 0.01 은 비용을 물리는 게 아니라 **잡음 전환 하나를 막아 주고 있었다.**

**세 측정의 종합**: 문턱을 낮춰도(−0.0009), 바닥을 없애도(0.0000), 높여도(−0.0050) 이득이
없다. selective3 가 cascade-routing 에 못 미치는 원인은 **채택 규칙이 아니다.**
기본값 복원 후 커밋된 아티팩트를 **6개 정책 전부 소수점까지 재현**했다.

### 3.3 그리고 고치는 과정에서 결함을 하나 만들었고, 테스트가 잡았다

`need` 를 게이트와 같은 `max(margin, se_k·SE)` 로 썼더니 `se_k·SE ≥ 0` 이라 **음수 margin 이
0 으로 바닥을 맞았다** — `margin=-1e9` 로 대안을 강제하는 기존 API 계약이 조용히 깨졌고
`test_submission.py::test_adapter_deploys_selective_router` 가 즉시 실패했다.

**테스트를 고치지 않고 규칙을 고쳤다** — `margin + se_k·SE` 로 바꾸면 `se_k=0` 에서 Phase 20
규칙과 **정확히** 같다. D22·D51("테스트가 결함을 지킨다")의 반대 사례다: 여기서는 **테스트가
내가 만든 조용한 계약 파기를 잡았다.** Phase 20 이 push 경로를 방벽 안에 넣은 것이 값을 했다.

★ **§3 전체가 이 Phase 에서 가장 값진 부분이다.** 감사의 진단은 그럴듯했고 저장소의 다른 절
(§4.5.1)이 뒷받침하는 것처럼 보였는데 **틀렸다.** 그리고 "옳아 보이는 개선"(SE 추가)이
실제로는 손해였다. **지적을 받았다고 바로 반영하면 안 되고, 지적도 측정 대상이다** (D69).
이것은 Phase 20 §2.6 이 감사의 demo 해석을 측정으로 기각한 것의 2회차다.

## 4. D65 — 예측력은 크게 올랐는데 **점수는 안 올랐다**

`src/encoder_scan.py` 를 만들어 인코더를 `p̄` 의 held-out log-loss 로 쌍대 비교하게 했다
(리플레이가 아니라 예측력으로 재는 이유: 인코더는 `p̄` 를 통해서만 정책에 들어간다.
판정 지표를 AUC 가 아니라 log-loss 로 둔 이유: `p̄` 는 `σ = 1 − λc/p̄` 에 **확률 값 그대로**
들어가므로 순위가 아니라 **보정**까지 봐야 한다).

측정 (textworld, 3-fold 쌍대):

```
hashing512   log-loss 0.5793   AUC 0.7810   Δloss +0.0897 (3.3×SE)   채택
hashing256   log-loss 0.6221   AUC 0.7605   Δloss +0.0469            미달
hashing96    log-loss 0.6690   AUC 0.7415   (기준 = 현행 기본값)
```

**예측기 품질이 크게 올랐다.** 96 차원은 문자 3-gram 해싱의 충돌이 심했다.

그런데 종합 점수로 재니 **LPB 는 오히려 −0.0013** 이었다 (fast −0.0055 / balanced +0.0041 /
premium +0.0014). 즉 **더 나은 p̄ 가 더 나은 점수로 자동 전환되지 않는다.**

이것은 세 가지와 **정합한다**:
1. §2.2 의 예측기 여지 +0.0123 (9.2%) — 작다.
2. Phase 19 의 예측기 용량 확장 6종 전부 회귀.
3. ★ 외부 문헌: arXiv:2606.07587 *The Routing Plateau* 가 21개 라우터에서 같은 천장을
   보고한다. **독립적인 두 측정이 같은 곳을 가리킨다.**

그리고 fast tier 가 **가장 크게 나빠졌다**(−0.0055)는 것이 D67 과 맞물린다 — fast 는 여지가
8% 뿐인 구간이고, 거기서는 예측이 좋아져도 예산이 허락하지 않는다.

### 4.1 그래서 쌍대 SE 까지 쟀고, 판정이 갈렸다

점추정 +0.0054(제출 대상)는 D21 절대 문턱 0.005 **바로 위**다. 그것만으로 기본값을 바꾸는
것은 D21·D26·D34 가 반복해 처벌받은 실수 그대로라, 같은 fold·시드에서 **인코더만 교체**한
쌍대 A/B 를 따로 만들었다 (`eval/probe_encoder_axis.py`).

| 정책 | 96 | 512 | Δ | 쌍대 SE | 요구 | 판정 |
|---|---|---|---|---|---|---|
| LPB 단독 | 0.5024 | 0.5011 | −0.0013 | 0.0025 | 0.0050 | **미달 (회귀)** |
| **selective3 (제출 대상)** | 0.5057 | **0.5111** | **+0.0054** | 0.0041 | 0.0050 | **통과** |

★ **부호가 갈린 것이 이 실험의 핵심 정보다.** LPB 단독은 fast 에서 **−2.0×SE** 로 유의하게
회귀하는데, selective3 는 세 tier 전부 +0.7~0.8×SE 로 같은 부호다. 기전을 보면 전환이
{cr:4·learned:1·lpb:4} → {cr:5·lpb:4} 로 바뀌었다 — 즉 이득은 **"라우팅이 좋아졌다"가 아니라
"고르기가 좋아졌다"** 다. 더 나은 `p̄` 가 메타 선택의 판별력을 올린 것이다.

D56 이 가르친 대로 **판정 대상은 제출 대상**이므로 통과다. 그래서 **배포 기본값만**
`hashing:512` 로 바꾸고 `get_encoder("hashing")`(=96)은 그대로 둔다 — 전역 기본값을 바꾸면
커밋 아티팩트 20 Phase 치가 한꺼번에 무효가 되고 그 대가는 합성 세계의 +0.0054 다.

**정직한 결론**: 감사 권고 "인코더에 투자하라"는 **부분적으로 옳았다.** 예측기 지표는 크게
올랐고(3.3×SE), 점수는 **제출 대상에 한해 문턱을 8% 차이로 겨우 넘었으며**, 라우팅 정책
자체는 오히려 나빠졌다. 셋을 다 적는 것이 정확한 보고다. 실데이터에서는 `--scan-encoders`
가 다시 판정한다 — 한국어 프롬프트에서는 해싱 96 의 손해가 여기보다 클 수 있다.

## 4.5 ★ D70 — 고치려고 만든 코드가 **다른 결함을 찾아냈다**

`demo.py` 에 [5] 제출 규약 실연(텍스트 프롬프트 + 단가 메타데이터)을 붙이자 **즉시 죽었다**:

```
ValueError: 프롬프트가 텍스트인데 이 라우터에 text_encoder 가 없습니다
```

`demo.py` 는 `ds.features = get_encoder("hashing").encode(...)` 로 인코더를 **익명으로 쓰고
버렸다.** D36 이 만든 계약("특성을 만든 인코더를 데이터셋에 실어라 → fit() 이 물려받아
어댑터까지 흘러간다")이 **데모에는 적용되지 않은 상태**였고, 저장소 전체를 훑어 보니
**21개 파일이 전부 같았다.**

왜 9 Phase 동안 안 걸렸나: **오프라인 경로는 특성 행렬만 쓴다.** 인코더 객체는 배포에서만
필요하고, 없어도 **아무 점수도 이상해지지 않는다.** Phase 20 §0 이 진단한 그 성질 그대로다.

### ★★ 그리고 여기서 **내가 낸 처방을 스스로 기각했다 (D71)**

첫 처방은 이랬다: "21개를 고치는 것으로 끝내면 22번째에서 재발한다. `LPBRouter.fit()` 이
인코더 없이 적합될 때 **경고**하면 모든 소비 지점이 동시에 덮이고 앞으로 생길 지점도
자동으로 덮인다." D62 를 사람의 점검 목록이 아니라 코드로 옮기는 것이니 옳아 보였다.

**측정으로 기각했다.** 경고를 넣고 `pytest -W error::RuntimeWarning` 을 돌리니
**108개 중 41개(38%)가 실패**했다 — 전부 오탐이다. **이미 인코딩된 특성 벡터를 넘기는 것은
정당한 지원 모드**이고(ablation·합성 6세계·회귀 스위트가 전부 그렇다), 그 다수 경우에
경고가 울린다.

**교훈 (D71): "모든 곳을 한 번에 덮는 기구"가 언제나 옳지는 않다.** 정당한 다수를 오탐하는
기구는 결함 1건을 막는 대가로 **경고 체계 전체를 마비시킨다** — 사람이 경고를 무시하도록
훈련시켜 *다음* 진짜 경고를 죽인다. 이미 정확한 기구가 있었다(`_features` 의 ValueError:
텍스트 입력 + 인코더 부재라는 **정확히 그 조건**에서만 발동하고 메시지가 실행 가능하다).

그래서 조치를 갈랐다: ① 21개 소비 지점 일괄 수정 ② 회귀 2종으로 고정(데모의 계약 ·
텍스트×단가 동시 관통). **D68 이 요구한 "마지막 화살표의 검사 기구"는 여전히 미해결**이고,
이 시도가 그 기구를 만들 때 **정밀도(precision)를 함께 재야 한다**는 조건을 하나 더 알려줬다.

## 5. 남긴 것 · 하지 않은 것

- **바꾼 것**: 게이트 배포 인코더 기본값 `hashing:512` (D21 통과, 단 1.3×SE) ·
  비용 규약 3형태 · 문항별 호출 상한 · 게이트 `--quick`/부분저장 · tier 여지 분해 상설화.
- **하지 않은 것**: **전역** 인코더 기본값(아티팩트 20 Phase 치 무효화 대비 이득 +0.0054) ·
  문턱을 유리한 쪽으로 조정 · fast tier 추가 최적화(여지 8%).
- **여전히 미해결**: 실데이터 0건 · 한국어 프롬프트 0건 · 학습형 베이스라인이 RouteLLM 급이
  아님(해싱 특성 로지스틱) · Routing Plateau 의 나머지 두 레버(더 큰 데이터·E2E 파인튜닝).
- **새 규칙 (D68)**: 각 Phase 는 **"지난 Phase 의 결론 중 코드에 반영되지 않은 것"** 목록을
  만든다. 측정 → 결론 → 행동의 마지막 화살표에 검사 기구를 둔다.
- **새 규칙 (D69)**: 외부 지적도 **측정 대상**이다. 그럴듯함과 저장소 내 유사 사례는
  근거가 아니다 (D66 이 실증).
